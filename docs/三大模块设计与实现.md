## 1. 整体需求说明

### 1.1 需求背景

原有系统只能**手动录入**情绪与随笔，痛点有三个：

| 痛点 | 表现 | 本次对策 |
|---|---|---|
| 记录成本高 | 每天要主动点开、选情绪、写文字，用户容易中断 | 无感记录：系统先替你"猜"，你只需确认或改一下 |
| 手机端不能看 | PC 版在手机上横向溢出、图表超屏 | 移动端响应式改造 + 底部导航栏 |
| 只回看不提示 | 长期低落没人提醒，等于数据没产生价值 | 情绪风险预警（多日数据才触发） |

### 1.2 范围与边界（一句话）

> **在不推翻原有代码结构的前提下，以"附加模块"的方式增加三项能力：**
> 轻量无感记录（IES）、移动端 H5 适配、情绪风险预警；
> 且把"隐私合规"与"非医疗诊断"两条红线写进代码注释、数据库注释与论文正文。

### 1.3 三条不可逾越的红线

```
┌──────────────────────────────────────────────────────────────┐
│ 红线一（隐私）：                                              │
│   不用摄像头/麦克风/录屏，不采键盘明文，不读 DOM 文本内容；    │
│   行为表内不存在任何文本列；数据仅本人可见（含管理员）。        │
│                                                              │
│ 红线二（自主权）：                                            │
│   推测永不自动写库 —— 只有用户点「保存」才生成正式日记，       │
│   且该条日记永久标记 source=2，任何时候可回溯它的来源。        │
│                                                              │
│ 红线三（非医疗）：                                            │
│   预警模块只输出"统计意义上的情绪关怀提示"，                   │
│   不出现任何疾病结论词，代码注释与 UI 均带免责声明。           │
└──────────────────────────────────────────────────────────────┘
```

### 1.4 改造策略：为什么用"附加"而不是"重构"

用户明确要求"**保留原有全部功能，无感是附加扩展模块，不推翻原有代码结构**"。因此：

- 数据库：`psy_diary` 只**增加**两列（`source` / `prediction_id`），旧数据 `source` 默认 1（手动），兼容零成本；
- 后端：新增包 `algorithm/` `config/Sense·Risk·Scheduler` `controller/Sense·RiskAlert`，**不修改任何既有 Controller**；
- 前端：新增一次性兜底层 `styles/mobile.css`，**不逐个文件改 CSS**；原有页面一行样式都不用动；
- 图表：通过升级 `composables/useChart.js`，原有 30+ 个图表调用点**无需任何修改**即获得响应式能力。

## 2. 无感记录模块业务流程

### 2.1 总体数据流（三路输入 → 融合 → 推测 → 用户确认 → 入库）

```
┌────────────────── 输入层（三路） ──────────────────┐
│  A 行为通路            B 文本通路        C 时序通路   │
│  前端端侧聚合并上报     即时推理不落库    已入库日记    │
│  psy_behavior_feature  随笔原文          情绪指数序列  │
│  (30s 批量 / 离开时)    (只在请求内存)    psy_diary     │
└──────────┬────────────────┬──────────────┬─────────┘
           │                │              │
    加权 KNN(K=5)     九类词典打分      AR(1) 外推
    7 维特征向量      否定翻转+程度副词    一阶自回归
           │                │              │
           └────────► 自适应加权融合 ◄──────┘
                          │
              confidence = P(top1) × √(参与通路数/3)
                          │
              < 0.45（可配）→ 不推荐，避免误导
                          │
              psy_emotion_prediction（confirm_status=0 待确认）
                          │
              ┌───────────▼────────────┐
              │  首页推测卡片 / 写日记页  │
              │「今天可能是『平静』？」    │
              └───────────┬────────────┘
       采用[1]    改了情绪再采用    忽略[2]    7 天未处理[3 自动过期]
                          │
              写 psy_diary(source=2, prediction_id=?)
                          │
          ══════►  只在这一刻，推测数据才升级为正式数据  ══════
```

### 2.2 关键分支：用户的每一次操作分别意味着什么

| 用户动作 | 后端行为 | 数据去向 |
|---|---|---|
| 点「保存」（用了推荐） | `confirm_status=1`，生成日记 `source=2`，记 `confirm_emotion` | 正式数据，但永久标"来自推测" |
| 点「保存」（改了情绪） | 同上，`confirm_emotion` 与 `suggest_emotion` 不同 → 记为**未命中样本** | 同上；差值用于算命中率 |
| 点「忽略」 | `confirm_status=2` | 不污染正式数据 |
| 不理会，7 天后 | 定时任务置 `confirm_status=3` | 自动过期，不打扰 |

> **这一步是整个模块的伦理核心**：系统永远只是在"提议"，决定权 100% 在用户手里，
> 而且连"我提议了什么、用户最终改成了什么"都被如实记下来，可以作为论文里的实验数据。

### 2.3 三通路算法（轻量化，无深度学习）

| 通路 | 算法 | 输入 | 输出 | 为什么选它 |
|---|---|---|---|---|
| A 行为 | 加权 KNN（K=5，高斯核加权） | 当日 7 维行为特征 vs 本人近 90 天 | 九类情绪概率分布 | 无训练过程，换用户即时生效；能指出"你和哪天最像"，可解释 |
| B 文本 | 最大正向匹配 + 否定翻转 + 程度副词缩放 | 用户随笔短文本 | 同上 | 词典可维护（213 条已入库），命中词可回传给用户看 |
| C 时序 | AR(1) 一阶自回归 + 趋势斜率 | 本人近 30 天情绪指数 | 明日指数预测值 → 映射到分布 | 一人一条序列，不需要外部训练集 |

**7 维行为特征**（每日一条，`BehaviorPredictor.vectorize`）：

```
x1 活跃强度    = 当日停留 / 本人近期均值       ← 用比值消除个体差异
x2 操作密度    = 当日点击 / 本人近期均值
x3 沉浸度      = 停留 / (活跃小时数 × 1h)      ← 上限 3.0
x4 夜间占比    = 22:00~05:59 活跃小时 / 活跃小时
x5 日记场景占比 = 写日记页停留 / 当日总停留
x6 FM 场景占比  = FM 页停留 / 当日总停留
x7 打开频次    = 当日进入次数 / 近期均值
```

**防自证循环**（重要，答辩常被问）：KNN 的历史标签**只取 `psy_diary.source=1` 的手动记录**。
如果再把推测出来的数据喂回去，误差会被不断放大 —— 这是"推荐系统自己给自己打分"的经典陷阱。

### 2.4 前端采集器的隐私落地（`utils/senseTracker.js`）

```
❌ 不监听 keydown / keyup / input / paste
❌ 不读取任何 input.value、textarea.value、DOM innerText
❌ 点击事件里只对计数器 +1，不看 event.target 是什么元素
❌ 不读 URL query、localStorage 内容、剪贴板
✅ 只统计：某个场景待了多少毫秒、进了几次、点了几次、哪些小时活跃过
✅ 30 秒批量上报；页面隐藏即暂停计时；离开页面前 flush
✅ 收到后端 401/403 立刻自我停用（fail-safe）
```

### 2.5 开关语义：总开关是「急停」，子开关是「意图」

| 开关 | 语义 | 关闭时发生什么 |
|---|---|---|
| 总开关 `sense_enabled` | 急停（kill switch） | 立即停止全部采集：`report` / `generate` 一律 403，前端采集器收到 403 自我停用 |
| 行为子开关 `sense_behavior` | 用户是否同意采集行为特征 | 只停行为通路 |
| 文本子开关 `sense_text` | 用户是否同意当次文本分析 | 只停文本通路 |

**真正的采集条件 = `enabled && 子开关`**，两个条件都在服务端判断，与界面显示无关。

> 早期实现是「关总开关时顺手把两个子开关也置 0」。看起来更"干净"，实际是个坑：
> 用户关一次再打开，子开关已经被系统悄悄改成了 0，界面却显示总开关已开启 ——
> 表现就是「开了却没数据」，而用户根本不知道是自己（还是系统）关掉了子开关。
> 现在总开关只做急停，不覆写用户的选择；关掉期间即使子开关显示为开，也不会产生任何采集。
>
> 顺带一条：`/sense/config` 只在**值真的变化**时写隐私日志。原来每次保存都写一条 `SWITCH`，
> 用户连点几次就把 `GRANT`/`REVOKE` 挤出「最近 50 条」，这份"可审计"证据链反而失效。

## 3. 移动端响应式改造方案

### 3.1 问题定位：先找到"到底是谁在溢出"

改造前实测存在横向滚动条的页面与根因：

| 页面 | 溢出源头 | 原写法 |
|---|---|---|
| 全站 | 左侧悬浮 `.box` + 内容区 `padding-left: 190px` | PC 专有 |
| Test.vue | `.trend-svg { min-width: 500px }` | 写死宽度 |
| Assistant.vue | `.session-sidebar { min-width: 260px }` | 写死宽度 |
| DataBoard.vue | `.flex-1/.flex-2 { min-width: 300px }` | 写死宽度 |
| Profile.vue | `.hero-info { min-width: 200px }`、`.lt-input { min-width: 220px }` | 写死宽度 |
| WriteDiary.vue | `.sf-int-btn { min-width: 140px }` | 写死宽度 |
| 图表 | 容器高度写死 `height: 280px` | 窄屏占比过高 |

### 3.2 解决方案：一层全局兜底 + 一处核心升级

不做"逐页重写"，而是**三层递进**：

```
第 1 层 —— 全局安全网  src/styles/mobile.css
  · * { box-sizing: border-box }          消除 padding 撑宽
  · html, body { overflow-x: clip }        clip 而非 hidden：
                                          不会创建滚动容器，也就不会破坏 position:sticky
  · 隐藏 PC 专属悬浮栏，清零 padding-left
  · 逐个把已定位的 min-width 改成 min-width: 0 / auto
  · 表单字号 ≥16px                         iOS 聚焦时不再自动放大整个页面
  · .mobile-tabbar                        新增底部导航 + env(safe-area-inset-bottom)

第 2 层 —— 布局降级   各断点媒体查询 ≤1024 / ≤768 / ≤375
  · .panel-row 由两列自适应为单列
  · 按钮组在 ≤700px 时每个按钮撑满一行（触摸友好）
  · 心情选择按钮在 ≤375px 时变两列 grid

第 3 层 —— 图表自适应  composables/useChart.js（见第 7 节）
  · ResizeObserver + 断点跨越时重新生成完整 option
```

### 3.3 为什么要在 PC 之上"叠加"而不是"切换到"手机版

用户要求"**一套代码兼容 PC + 手机 H5**"。因此采用的是**渐进增强**而非双套模板：

- 断点是 addon：小屏追加/覆写样式，而 PC 样式原样保留；
- 顶部悬浮导航在手机上这属于 "hover 才能出现" 的交互，**手机没有 hover** → 补充底部 tabbar，两套导航共存、各自在自己的断点显隐；
- 桌面访问体验与改造前完全一致，回归风险最小。

### 3.4 移动端"必须有"的三个细节

1. **底部导航**：原导航栏藏在顶部 hover 里，手机上永远点不出来 → 新增 5 项 tabbar，"我的"带预警未读红点；
2. **iOS 表单 16px 规则**：字号小于 16px 的输入框聚焦时 Safari 会强制放大整个页面，破坏布局；
3. **安全区适配**：iPhone 底部圆角 / Home Indicator 会盖住 tabbar → `padding-bottom: env(safe-area-inset-bottom)`。

## 4. 情绪风险预警判定规则

### 4.1 为什么必须看窗口内的多日数据，而不是单次触发

> 单次难过是正常人类情绪。只有**窗口期内的负面占比、低落天数、下滑趋势**三个指标共同越界，
> 才判为需要关注 —— 这既是统计上的严谨性，也是伦理上的克制。

### 4.2 判定流程（`RiskRuleEngine.judge`）

```
取最近 N 天（默认 7）的每日情绪
        │
        ├─ 有记录天数 < minRecordDays（默认 4）→ 数据不足，不判定（避免小样本误报）
        │
        ├─ ① 窗口内低落 ≥ 5 天                        → 三级「高度关注」
        │  ② 负面占比 ≥ 75% 且平均情绪指数 ≤ 35        → 三级「高度关注」
        │
        ├─ 窗口内低落 ≥ 3 天                          → 二级「中度提醒」
        │
        ├─ 负面占比 ≥ 50% 且情绪指数斜率 ≤ -1.5 且低落 ≥ 2 天  → 一级「轻度关注」
        │
        └─ 其余情况 → 不打扰（level=0）
```

### 4.3 一个刻意的取舍：判据是「窗口内低落天数」，**不声称**「连续」

早期实现用的是「最长连续低落天数」。但情绪日记天然有漏记，而这个判据的两条路都不成立：

- **严格要求日期相邻**：真实数据里「连续 5 天低落」几乎不可能出现（用户即使状态不好也未必天天写），
  预警会长期不触发，属于漏报；
- **允许跨越缺失日累加**：那它算出来的已经不是「连续」——旧代码正是这种，`prev` 变量赋值后
  从未参与任何判断（`run = prev == null ? 1 : run + 1`），实际语义退化成「永不打断」，
  却对用户输出「你已经连续 N 天情绪低落」。

因此判据统一为**窗口内低落天数**：语义单一（就是数天数）、可直接复现、与负面占比同源
（两者都是「窗口内计数」，只是情绪集合不同）。对外文案不再出现「连续」二字，
并由单元测试 `adviceMustNotClaimContinuity` 守住——一旦有人改回「连续」措辞，测试直接失败。

### 4.4 防打扰设计（`RiskAlertServiceImpl.evaluate`）

| 机制 | 实现 |
|---|---|
| 同日唯一 | `(user_id, alert_date)` 唯一键，天然去重 |
| 冷静期 | 最近 `cooldownDays`（默认 3）天内已发过同级/更高级预警 → 不再打扰 |
| 等级提升才重弹 | 已存在记录但新判定等级更高时才重置未读；同级不重复打扰 |
| 用户可确认 | 点「我知道了」→ `ack_status=1`，本次预警不再弹窗 |

### 4.5 阈值全部可配置（`application.yml → app.alert.*`）

```yaml
app:
  alert:
    enabled: true
    window-days: 7            # 观察窗口
    min-record-days: 4        # 窗口内至少有多少天有效记录才判定
    require-multi-day: true   # 一级预警是否要求低落天数 ≥ 2
    level2-downcast-days: 3   # 二级：窗口内低落天数
    level3-downcast-days: 5   # 三级：窗口内低落天数
    level3-ratio: 0.75        # 三级：负面占比
    level3-avg-index: 35.0    # 三级：平均情绪指数上限
    level1-ratio: 0.5         # 一级：负面占比
    level1-slope: -1.5        # 一级：趋势斜率上限（每天下降点数）
    cooldown-days: 3          # 冷静期
    disclaimer: "本提示仅基于你自行记录的情绪数据做统计参考，不属于医疗诊断，不能替代专业评估。"
```

> **答辩演示技巧**：改完 yml 重启后端，在个人中心 → 情绪预警 Tab 点「手动触发一次判定」，
> 当场就能看到不同阈值的效果，"可配置"这件事从口头承诺变成了可演示的事实。

### 4.6 预警内容三段式（后端 `RiskRuleEngine.advice` 分级生成）

```
① 温馨提示  —— 「绪见注意到，最近 7 天里，有 N 天你记录到的情绪偏低落。这段时间一定很不容易，请先别责怪自己。」
② 自我调节建议 —— 三条可执行的具体小事（吃饭/晒太阳/写日记/听 FM/出门走走），不是空话
③ 求助引导  —— 给出心理援助热线与咨询渠道，措辞是"可以试着联系"而不是"你该去看医生"

【重要】本提示仅基于你自行记录的情绪数据做统计参考，不属于医疗诊断，不能替代专业评估。
```

### 4.7 前端的两道保险

- `RiskAlertDialog.vue`（全局弹窗，挂在 `AppLayout`，登录后任意页面最多弹一次）：顶部 + 底部双处免责声明，固定求助资源位；
- `RiskAlertCard.vue`（首页常驻消息卡）：点过"我知道了"后自动收起；
- 预警历史在 个人中心 → 情绪预警 Tab，包含触发依据原文与当时的阈值。

```sql
INSERT INTO psy_behavior_feature (...) VALUES (...)
AS new ON DUPLICATE KEY UPDATE
  stay_ms    = psy_behavior_feature.stay_ms   + new.stay_ms,

```

### 5.4 隐私的关键落点：**物理隔离，不是逻辑判断**

```java
// BehaviorFeatureMapper.java —— 每一条 SQL 都强制带 user_id，
// 包括管理员在内，想查别人的数据在持久层就被挡住了。
@Select("SELECT * FROM psy_behavior_feature WHERE user_id = #{uid} AND stat_date BETWEEN #{from} AND #{to}")
List<BehaviorFeature> selectRange(@Param("uid") Long uid, ...);
```

后端刻意**不提供**"按 userId 查他人行为数据"的接口 —— 没有 `getBehaviorByUserId` 这个方法，
而不是"提供了但判断一下权限"。这样在答辩时可以说：**"权限边界是用'没有这条路径'来保证的，不是靠 if 判断。"**

### 5.5 同一天写多篇日记，哪一篇代表"今天"？

`psy_diary` **允许**同一天写多篇（这是功能，不是缺陷），但所有按天统计的接口都必须回答
同一个问题：这一天算哪种情绪？当前库里有 12 组同日多篇（共 30 行），如果没有统一规则，
同一天在不同图表里会出现不同的值。

**唯一裁决规则：`diary_id` 最大（当天最后写的那篇）代表当天。**

| 位置 | 实现 | 说明 |
|---|---|---|
| `StatisticsMapper.myDiaryAgg / myDiaryBetween` | `INNER JOIN (SELECT MAX(diary_id) ... GROUP BY diary_date)` | SQL 侧显式取最后一篇 |
| `SenseServiceImpl.loadEmotions` | `ORDER BY diary_date, diary_id` + `map.put` 覆盖 | 排序必须带 `diary_id` |
| `RiskAlertServiceImpl.loadEmotions` | 同上 | 与统计侧同一口径 |
| `ModelEvaluationTest` | 同上 | 评估脚本也遵守同一规则 |

> **为什么排序必须带 `diary_id`**：MySQL 对 `ORDER BY diary_date` 的并列行不保证顺序，
> 而 Java 侧是「后者覆盖前者」的写法。只按日期排序时，胜出的是哪一篇是**不确定的**，
> 于是同一天、趋势图和预警可能取到不同的日记 —— 这类 bug 不报错，只是数字对不上，
> 极难排查。
>
> **为什么不加 `(user_id, diary_date)` 唯一键**：加唯一键等于"一天只能写一篇"，
> 需要合并现有数据，属于产品语义变更而不是缺陷修复。若后续决定改成一天一篇，
> 应先做数据合并脚本再加约束。当前只解决"取值不确定"。
>
> 配套索引 `idx_uid_source_date_id (user_id, source, diary_date, diary_id)`
> 让上述子查询走 index-only scan（见 `sql/migration/20261029_diary_day_rule.sql`）。

## 7. ECharts 移动端适配方案

### 7.1 四层保障

```
① 容器层  —— 图表容器宽度 100%，高度用 clamp(最小值, 视口相关值, 最大值)
             .chart { height: clamp(200px, 34vw, 280px) }
             保证图表永远跟着容器走，而不是跟着一个写死的 px 走

② 重绘层  —— useChart 内置 ResizeObserver 监听容器自身尺寸变化
             + window.resize + orientationchange（手机横竖屏切换必须监听）
             + 首帧 c.resize()：容器由 v-if 刚渲染出来时尺寸还是 0

③ 加工层  —— set() 内部自动套 applyMobileOption(option)：窄屏下改写 grid /
             tooltip.confine / legend / axisLabel / 日历 cellSize / visualMap，
             并记住原始 option，**断点跨越时重新加工一遍**
             → 30+ 个既有调用点一行不改就拿到了移动端适配

④ 空态层  —— series 全空时给容器打 data-empty，由 CSS 显示「暂无记录」
             否则用户无法区分「没有数据」「还在加载」「加载失败」三种状态
```

另外，数据看板的 16 个图表用 `useChart(el, name, { lazy: true })` **进入视口才 init**
（IntersectionObserver + 240px 预取），首屏不再同时创建 16 个画布。

### 7.2 断点系统

```js
export const BREAKPOINTS = { XS: 480, SM: 768, MD: 1024 }
// XS=手机竖屏  SM=手机横屏/小平板  MD=平板  LG=桌面
```

`applyMobileOption(option, bp)` 自动做的事：

| 项 | 桌面（lg） | 手机（xs / sm） |
|---|---|---|
| grid | 不动 | 补默认值 `left: 4/8, right: 10/14, containLabel: true`（已显式写过的字段不覆盖） |
| tooltip | 默认跟随鼠标 | `confine: true`（**必须**，否则气泡会溢出屏幕）+ 字号 10/11 |
| legend | 不动 | 压到顶部居中、图标缩小、字号下调（不再沉底压 x 轴） |
| xAxis 标签 | 横排 | `rotate: 45` + `hideOverlap: true` |
| 日历热力图 | `cellSize: ['auto', 18]` | `['auto', 11/13]`，否则一年 53 列横向溢出 |
| visualMap 连续条 | 竖排右侧 | 横排居中、变短 |
| title | 不动 | 字号 12/13 |

> 桌面断点直接返回**同一个对象**（不拷贝），所以桌面端零额外开销。

### 7.3 用法（已有 30+ 调用点零改动）

```js
// ① 常规写法：写桌面版 option 就行，窄屏加工由 useChart 内部完成
trendChart.set({ grid: {...}, xAxis: {...}, series: [...] })

// ② 需要整份重排时（例如手机上要把图例挪到底部、隐藏次要坐标轴）
dualChart.setResponsive((bp) => {
  const narrow = bp === 'xs' || bp === 'sm'     // 断点值是小写
  return {
    legend: { left: narrow ? 'center' : 'right' },
    grid:   { left: narrow ? 8 : 44 },
    xAxis:  { axisLabel: { rotate: narrow ? 45 : 0 } },
    series: [ /* ... */ ],   // ⚠️ 必须返回完整含 type 的 series
  }
})

// ③ 首屏图表多时开启懒初始化
const heatChart = useChart(heatRef, 'heat', { lazy: true })
```

> ⚠️ 踩坑记录 1：`applyMobileOption` 早期用 `JSON.parse(JSON.stringify(option))` 做深拷贝，
> 会把所有 `formatter` **函数**变成 `undefined`。它一直没炸只是因为当时没人调用；
> 一旦接上自动加工，全站 tooltip 会同时变空白且不报错。现改为保留函数的递归深拷贝，
> 并由 `frontend/scripts/verify_chart_utils.mjs` 守住（21 项断言，含懒加载调度）。

> ⚠️ 踩坑记录：ECharts 6 下 `notMerge: true` + 只写部分字段会导致 series 丢失 `type` 而崩溃。
> 所以 factory **必须返回完整 option**，这一点已写进 `useChart.js` 的注释。

### 7.4 新增图表与"真实 vs 推测"的视觉区分

```
实线 + 面积渐变 + 主题色  = 用户亲手记录的真实情绪
虚线 + 空心圆点 + 淡紫色  = 系统推测后经用户确认的记录
```

这张双序列图是无感模块**最重要的可视化产出**：它让"系统参与了多少、用户最终改了多少"一眼可见，
也直接支撑论文里"推测采纳率/命中率"的论证。

数据看板另有三张行为关联图：

- **停留时长 × 情绪指数散点**（点径随停留时长变化，颜色按情绪类别）
- **活跃时段 × 情绪热力图**（24 小时 × 9 类情绪）
- **低情绪日 vs 高情绪日雷达**（对比 7 维行为特征的差异）

## 8. 可直接放进论文的章节（创新点）

> 以下文字已按论文口吻写好，可直接复制到 **第 3 章 系统设计** 与 **第 5 章 总结与展望**。
> 建议把"非医疗诊断"和"数据权限"两小节单独成段 —— 答辩时老师最关心的就是这两个风险点。

### 8.1 创新点一：面向隐私保护的轻量级无感情绪感知机制

（论文 §3.4）

> 针对传统情绪追踪系统依赖手动录入、长期留存率低的问题，本文设计并实现了一套**轻量级无感情绪感知（Imperceptible Emotion Sensing, IES）**机制。
> 该机制在数据采集阶段即贯彻最小化原则：不使用摄像头、麦克风与屏幕录制，不采集键盘输入明文，不读取页面 DOM 文本内容，
> 仅记录用户在指定功能场景下的停留毫秒数、进入次数与点击次数三类聚合数值，并在浏览器端先行聚合成"日—场景"粒度后才上传服务端。
> 原始文本仅在做情感分析时于当次请求的内存中存活，分析结果只保留命中的词典词条，**原文不写入任何数据表、不输出至系统日志**。
>
> 在推理阶段，系统采用"加权 K 近邻 + 中文情绪词典 + 一阶自回归"三通路融合的轻量算法。
> 其中 KNN 以用户本人近 90 天的七维行为特征为样本空间，词典通路处理用户随笔的即时语义，时序通路则由历史情绪指数序列外推。
> 三路结果按参与通路数自适应加权融合，并以"首类概率与通路完整度的几何平均"作为置信度；
> **置信度低于阈值（默认 0.45）时系统主动放弃推荐**，以避免低质量推测误导用户。
> 相较深度学习方案，该方法无需离线训练、单次推理耗时低于 5 ms，可在单机轻量部署，具备良好的可迁移性。
>
> 在数据安全层面，本模块采用**知情授权（opt-in）**模式，默认关闭，用户可随时启闭并一键清除全部历史行为数据，系统亦按 180 天周期自动清理。
> 所有涉及行为数据的查询接口均以 JWT 中的用户标识为准，**系统未提供任何按用户标识查询他人行为数据的接口**，
> 即在持久层以"不存在该查询路径"而非"查询后再鉴权"的方式实现数据隔离，管理员亦不例外。
>
> 值得强调的是，本机制的输出**永远不作为最终记录**：推测结果以候选形式提交用户确认或修改，
> 只有用户主动提交后才写入正式日记，且该条记录会被永久标记为"系统推测来源"，可随时回溯。
> 系统同时记录"推荐值"与"用户最终确认值"的差异，作为推测准确率的评估样本，形成闭环学习所需的数据基础，
> 且为避免自证循环，KNN 的训练样本**仅取自用户手动录入的记录**。

### 8.2 创新点二：基于滑动窗口的情绪风险预警（非医疗诊断）

（论文 §3.5）

> 在情绪的长期追踪过程中，若仅提供数据回看而无法识别异常趋势，系统的实用价值有限。
> 本文设计了一套**基于滑动窗口的情绪风险预警规则引擎**。为避免对单次负面情绪的过度反应，
> 引擎以最近 7 天（可配置）为观察窗口，综合"负面情绪占比""窗口内低落天数""情绪指数趋势斜率"三项统计量进行分级判定，
> 并要求窗口内有效记录不少于 4 天方予以判定，以规避小样本误报。
> 判据采用**窗口内低落天数**而非"最长连续低落天数"：自报数据中的漏记无法区分"心情尚可"与"忘记记录"，
> 任何"连续性"都只能靠假设支撑；改为计数后语义唯一、可复现，对外文案也不再声称连续。
> 同时通过唯一键约束、冷静期（默认 3 天）与等级提升触发三重机制防止重复打扰。
>
> 系统据此输出"轻度关注—中度提醒—高度关注"三级提示，内容包含温馨提示、可执行的自我调节建议与专业求助渠道引导。
>
> **需要特别说明的是：本预警模块的输出仅为用户情绪数据的统计提示，不属于医疗诊断范畴，不能作为抑郁症或其他精神疾病的诊断依据。**
> 系统在设计上刻意避免输出任何疾病结论性判断，且在接口响应、前端弹窗与历史记录页三处均强制携带免责声明。
> 如用户出现持续不适，仍应以专业医疗机构的评估意见为准。

### 8.3 创新点三：面向移动端 H5 的渐进式响应式适配方案

（论文 §3.6）

> 为使同一套前端代码同时适用于桌面浏览器与移动设备，本文采用渐进增强而非双套模板的响应式方案。
> 改造过程中对既有页面进行了横向溢出溯源，识别出固定像素宽度、非盒模型计算、隐藏式悬浮导航等若干类典型成因，
> 并在此基础上建立三层适配设施：其一为全局安全网，统一盒模型并采用 `overflow-x: clip` 约束（该取值不会创建滚动容器，
> 因而不会破坏页面内既有的粘性定位）；其二为断点降级布局，使多栏面板在窄屏环境下自动变为单列、
> 表单控件与按钮按触摸尺度重排，并将输入控件字号提升至 16 px 以上以避免 iOS 浏览器的聚焦缩放行为；
> 其三为图表自适应，为 ECharts 图表容器引入 ResizeObserver 与断点感知机制，
> 在跨越断点时重新生成完整的图表配置对象，从而在移动端自动压缩布局边距、旋转坐标轴标签、限制浮层边界，
> 确保图表不溢出屏幕且不丧失可读性。
> 该方案无需修改既有业务组件代码，桌面端原有视觉与交互效果保持不变。
