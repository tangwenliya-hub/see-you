# 轻量级无感记录模块（IES）设计与实现方案

> IES = Imperceptible Emotion Sensing（无感情绪感知）
> 所属项目：基于 SpringBoot + ECharts 的个人长期情绪追踪可视化系统设计与实现
> 技术栈不变：SpringBoot 3.3.5 + MyBatis-Plus + MySQL 8.4 + Vue 3.5 + ECharts 6

---

## 0. 设计红线（先立规矩，再写代码）

本模块涉及用户行为数据，**隐私合规是它的生命线**，所有设计必须在以下红线内：

| 红线 | 具体约束 |
|---|---|
| R1 数据最小化 | 只采集**聚合后的数值**（停留毫秒数、点击次数、进入次数、时段位图），不采集任何内容 |
| R2 不采集明文输入 | 不监听 keydown/keyup/input/paste；不读取表单 value；不读剪贴板、URL query、localStorage 内容 |
| R3 原文不落库 | 短文本情感分析的原文**仅在当次请求内存中存活**，不写入任何表、不打 INFO 日志 |
| R4 无传感 | 不调用摄像头、麦克风、陀螺仪、GPS、蓝牙；不使用第三方 Cookie、不用 Canvas 指纹 |
| R5 默认关闭 | 采用 **opt-in**（默认关闭）而非 opt-out，必须用户显式授权后才启用 |
| R6 仅本人可见 | `userId` 一律取自 JWT，**任何角色（含管理员）都无权查询他人的行为特征与推测结果** |
| R7 推测不代笔 | 系统推测结果**永远不自动入库**，必须经用户确认才写入正式日记，且永久标注来源 |
| R8 可撤回 | 一键关闭开关 + 一键删除全部行为数据；数据默认保留 180 天，到期定时清理 |

> 这 8 条建议**原样复制**到论文 4.x 节，并在答辩 PPT 上单独做一页——它把"隐私风险"从被动挨打题变成主动得分题。

## 1. 业务流程

### 1.1 总体数据流（三路输入 → 融合 → 推测 → 确认 → 入库）

```
┌──────────── 输入层（三路） ────────────┐
│ A 行为通路    B 文本通路     C 时序通路  │
│ 前端端侧聚合   即时推理不落库  已入库日记  │
│ ↓这个30s批量    ↓               ↓        │
│ psy_behavior   psy_diary文本    psy_diary  │
│ _feature       （原文不落库）   情绪时序    │
└────────┬───────────┬───────────┬─────────┘
         │           │           │
    KNN加权     词典情感打分   AR(1)外推
    最近邻        +否定翻转      一阶自回归
         │           │           │
         └─────► 加权融合 ◄──────┘
                    │
              Top1情绪 + Top3候选 + 置信度 + 理由
                    │
              psy_emotion_prediction（confirm_status=0）
                    │
              ┌─────▼──────┐
              │ 前端推测卡片 │「今天可能是『平静』，要记录吗？」
              └─────┬──────┘
        采用[1]  修改后采用  忽略[2]   7天未处理[3过期]
                    │
            写 psy_diary(source=2, prediction_id=?)
                    │
         ──► 只在此刻，推测数据才升级为正式数据
```

### 1.2 行为通路（A）时序细节

```
用户进入页面  ──router.afterEach──► 记 enterTime / sceneCode
用户在页面内  ──click（只 cnt++）──► 计数累加，不记录点击了什么
切换标签页    ──visibilitychange──► 隐藏时暂停计时（不把后台时间算成使用时长）
离开/30 秒到  ──flush─────────────► navigator.sendBeacon('/sense/behavior/report')
服务端接收    ──强制 userId=JWT──► upsert 到 psy_behavior_feature（同一天同场景覆盖合并）
```

关键设计：**端侧先聚合，服务端只收聚合值**。服务端永远不知道用户"几点几分点了哪个按钮"，只知道"日记页今天停留了 6 分 12 秒、点了 34 次"。

- 场景白名单（`scene_code` 枚举，共 7 个）：`home / diary / write / fm / test / community / profile`
- 路由不在白名单 → 归为 `home`，不逐个 URL 上报（避免 URL 泄露隐私）

### 1.3 文本通路（B）时序细节

```
用户在写日记框写随笔（草稿，未提交）
        │
        ▼ 点击「帮我识别情绪」（用户主动触发，非后台偷偷跑）
POST /sense/text/analyze   body: { text: "今天加班到十点，有点累" }
        │
   ┌────▼─────────────────────────────────────┐
   │ EmotionLexiconAnalyzer（纯内存）           │
   │  · 中文情绪词典匹配（psy_emotion_lexicon） │
   │  · 否定词翻转（"不开心"→负向）             │
   │  · 程度副词加权（"非常累"×1.5）            │
   │  · 9 类情绪打分 → 归一化                   │
   └────┬─────────────────────────────────────┘
        │ 返回 {emotion:3, intensity:2, confidence:0.71, hitWords:["累"]}
        ▼
   原文函数返回即销毁，不写表、不打日志
```

> 注意：`hitWords` 返回的是**命中的词典词**，不是用户原文，这是可解释性与隐私的折中点。若答辩被追问，可改为只返回命中的情绪类目不返回词。

### 1.4 推测触发时机

| 触发类型 | trigger_type | 时机 | 说明 |
|---|---|---|---|
| 系统定时 | 1 | 当日 20:00 定时任务 | 只为当天无日记且已开启无感记录的用户生成 |
| 用户主动 | 2 | 点「帮我猜一下」 | 实时计算，立即返回 |
| 文本即时 | 3 | 点「识别情绪」 | 只返回不建 prediction 记录（纯即时分析） |

同一用户同一天同一 trigger_type 唯一（唯一键约束），**一天最多打断用户一次**，避免骚扰。

### 1.5 关闭开关后的行为

```
用户关闭 sense_enabled
   ├─ 前端 senseTracker.destroy()：移除所有监听器、清空待上报队列、不再 sendBeacon
   ├─ 服务端所有 /sense/query 类接口返回空集合（403 → 不是"无权限"，而是"已关闭"）
   ├─ 已有数据保留 180 天（可随时重新开启继续使用）或用户点「立即清空」物理删除
   └─ 写一条 psy_sense_privacy_log(action='REVOKE')
```

## 2. 数据库设计

### 2.1 已有表新增字段

```sql
-- ========== 2.1.1 sys_user：无感记录开关（默认全关 = opt-in） ==========
ALTER TABLE `sys_user`
  ADD COLUMN `sense_enabled`  TINYINT      DEFAULT 0 COMMENT '无感记录总开关 0=关闭(默认) 1=开启' AFTER `profile_bg`,
  ADD COLUMN `sense_behavior` TINYINT      DEFAULT 0 COMMENT '行为特征采集子开关 0=关 1=开'      AFTER `sense_enabled`,
  ADD COLUMN `sense_text`     TINYINT      DEFAULT 0 COMMENT '文本情感分析子开关 0=关 1=开'      AFTER `sense_behavior`,
  ADD COLUMN `sense_grant_at` DATETIME     DEFAULT NULL COMMENT '用户授权时间（隐私审计用）'      AFTER `sense_text`,
  ADD COLUMN `sense_revoke_at` DATETIME    DEFAULT NULL COMMENT '最近一次关闭时间'                AFTER `sense_grant_at`;

-- ========== 2.1.2 psy_diary：区分数据来源 ==========
ALTER TABLE `psy_diary`
  ADD COLUMN `source`        TINYINT DEFAULT 1 COMMENT '数据来源 1=用户手动录入 2=系统推测后用户确认' AFTER `is_public`,
  ADD COLUMN `prediction_id` BIGINT  DEFAULT NULL COMMENT '来源为2时关联的推测记录ID（溯源用）'      AFTER `source`,
  ADD INDEX `idx_user_date` (`user_id`, `diary_date`);
```

> **为什么要加 `source` 字段？**
> 推测数据若不标注来源，就会与真实自评数据混淆，污染后续所有统计与二次训练（"自我实现的循环论证"）。
> 有了 `source`，所有的准确率报表、趋势图、均可手动/推测分色渲染，`source=2` 的数据默认不参与"再次训练特征权重"的计算，从工程上断掉数据污染链。

### 2.2 新增表

#### 表 P1：`psy_behavior_feature` — 脱敏行为特征表（**只有整数，没有任何文本**）

```sql
CREATE TABLE `psy_behavior_feature` (
  `feature_id`   BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键',
  `user_id`      BIGINT       NOT NULL                COMMENT '数据归属用户（查询强制以JWT为准）',
  `stat_date`    DATE         NOT NULL                COMMENT '统计归属日期（按服务端日期归档）',
  `scene_code`   VARCHAR(32)  NOT NULL                COMMENT '场景枚举: home/diary/write/fm/test/community/profile',
  `stay_ms`      INT UNSIGNED DEFAULT 0               COMMENT '该场景当日累计停留毫秒数',
  `visit_cnt`    INT UNSIGNED DEFAULT 0               COMMENT '当日进入该场景次数',
  `click_cnt`    INT UNSIGNED DEFAULT 0               COMMENT '当日该场景点击次数（仅计数，不记录点击对象）',
  `hour_mask`    INT UNSIGNED DEFAULT 0               COMMENT '24小时活跃位图，bit i=1 表示第i小时活跃过',
  `create_time`  DATETIME     DEFAULT CURRENT_TIMESTAMP,
  `update_time`  DATETIME     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`feature_id`),
  UNIQUE KEY `uniq_user_date_scene` (`user_id`, `stat_date`, `scene_code`),
  KEY `idx_user_date` (`user_id`, `stat_date`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='无感记录-脱敏行为特征表(仅数值，无文本)';
```

设计要点：
- **`hour_mask` 用 24 位整数存活跃时段位图**，而不是每小时一行或存 JSON。一天 7 场景最多 7 行 → 一个用户一年最多 2555 行，体积极小；位图做"夜间活跃占比"只需位运算，比 JSON 解析快且不存非结构化数据（论文里能写"拒绝存储非结构化行为日志"）。
- 容量估算：1000 用户 × 365 天 × 7 行 × 约 60B ≈ 150MB/年，完全可控。

## 3. 算法设计（轻量化，可写在论文里）

三个方法全部**无训练 / 无深度学习**，单次计算 < 5ms，单机 MySQL + Java 即可跑，符合"毕设难度可控"。

### 3.1 行为通路：加权 K 近邻（KNN，K=5）

对每一天构造 7 维特征向量并做用户内标准化（除以该用户近 90 天的均值/标准差）：

| 维度 | 含义 | 计算 |
|---|---|---|
| x1 | 当日活跃强度 | 总停留 ms / 近90天均值 |
| x2 | 当日操作密度 | 总点击数 / 近90天均值 |
| x3 | 沉浸度 | 总停留 / (最后活跃时 - 首次活跃时 + 1) |
| x4 | 夜间占比 | 22:00–06:00 停留 / 总停留（由 `hour_mask` 位运算得出） |
| x5 | 日记场景占比 | diary+write 停留 / 总停留 |
| x6 | 疗愈资源占比 | fm 停留 / 总停留 |
| x7 | 打开频次 | visit_cnt 合计 / 近90天均值 |

对目标日向量 $\vec{x_t}$ 与历史第 $i$ 天 $\vec{x_i}$ 计算欧氏距离 $d_i$，取最近的 K=5 天，按相似度加权投票：

$$w_i = \frac{1}{d_i + \varepsilon},\qquad P_{beh}(e) = \frac{\sum_{i \in TopK,\ y_i = e} w_i}{\sum_{i \in TopK} w_i}$$

其中 $y_i$ 是历史第 $i$ 天**用户自己手动记录**的情绪（`psy_diary.source = 1`），**刻意排除 source=2 的记录**，避免用推测数据训练推测模型的自我循环。

### 3.2 文本通路：词典加权打分

$$S_e = \sum_{k \in \text{hit}_e} w_k \cdot \text{neg}(k) \cdot \text{deg}(k),\qquad
P_{txt}(e) = \frac{S_e}{\sum_{j=1}^{9} S_j}$$

- `neg(k)`：若词前有否定词（窗口 3 字），取 −1，否则 1
- `deg(k)`：若前有程度副词，乘其倍数（如"非常"×1.5、"有点"×0.6）
- 全部未命中 → 返回 null，该通路不参与融合（不强行输出）

### 3.3 时序通路：一阶自回归 AR(1)

取该用户近 30 天情绪**指数**（复用现有 `EMOTION_INDEX` 映射：开心100/平静70/疲惫50/难过20/生气25/焦虑40/兴奋90/满足85/其他55），缺失日线性插值：

$$\hat{y}_{t+1} = \mu + \varphi\,(y_t - \mu),\quad
\varphi = \frac{\sum (y_i-\mu)(y_{i-1}-\mu)}{\sum (y_i-\mu)^2}$$

$\varphi$ 为一阶自相关系数，本身就是个有意义的量（$\varphi>0.6$ 说明情绪惯性强，可在 UI 上提示"你的情绪状态比较连贯"）。最后把连续值 $\hat{y}_{t+1}$ 按最近邻映射到 9 类情绪。

### 3.4 三路融合与置信度

$$P(e) = \alpha\,P_{beh}(e) + \beta\,P_{txt}(e) + \gamma\,P_{ser}(e)$$

| 可用通路 | α(行为) | β(文本) | γ(时序) |
|---|---|---|---|
| 三路齐全 | 0.30 | 0.45 | 0.25 |
| 行为+时序 | 0.55 | 0 | 0.45 |
| 行为+文本 | 0.40 | 0.60 | 0 |
| 仅行为 | 1.00 | 0 | 0 |

$$\text{confidence} = P(e_{top1}) \times \sqrt{\frac{\text{参与通路数}}{3}}$$

**低于 0.45 不产生推荐**，前端显示"数据还太少，再记几天我就能猜啦"。这条"宁可不猜也不瞎猜"的策略是论文里很好写的一笔。

可解释理由示例：
> 「你今天的使用节奏与 10 月 03 日很接近（那天你记录的是『平静』）；随笔里出现了『累』『赶 deadline』；近期情绪基线平稳 → 推测今天是**疲惫**，你可以修改后再记录。」

## 4. 接口设计

### 4.1 接口总表（后端统一前缀 `/sense`，全部需登录）

| # | 方法 | 路径 | 说明 | 权限规则 |
|---|---|---|---|---|

## 7. 论文创新点段落（可直接用）

### 7.1 创新点一：面向个人长期追踪的多源轻量情绪推测方法

> 现有情绪追踪系统的分析功能多停留在"对已记录数据的统计回放"，缺乏对用户当前情绪状态的前瞻性推断；而已有的情绪识别研究又高度依赖深度学习模型与大规模标注语料，难以在单机毕设环境中复现与解释。针对这一矛盾，本文提出一种面向单用户长期场景的**多源轻量情绪推测方法**：以用户自身的历史记录作为唯一语料，融合三条互补通路——① 基于行为特征加权 K 近邻的相似日匹配；② 基于自建九类情绪词典的短文本情感打分（含否定词翻转与程度副词加权）；③ 基于一阶自回归 AR(1) 的情绪序列外推。三路输出经自适应权重融合得到候选情绪分布，并按 $confidence = P(e_{top1}) \cdot \sqrt{n/3}$ 计算置信度，低于 0.45 时不输出推荐。该方法**无需训练过程、无第三方标注语料、单次推理耗时低于 5 ms**，在普通应用服务器上即可部署，同时每一步推理均可给出人类可读的依据，避免了黑盒模型的不可解释问题。

### 7.2 创新点二：隐私优先的无感感知架构

> 「无感采集」天然伴随隐私争议，是本类系统落地的最大阻力。本文将隐私保护从"事后说明"前移为"架构约束"，提出**隐私优先的无感感知架构**，其核心机制包括：① **数据最小化**——行为侧仅采集聚合数值（停留毫秒数、点击次数、进入次数、24 位活跃时段掩码），不采集 URL、不采集点击目标、不监听键盘明文、不调用任何音视频与生物传感器；② **端侧先聚合**——原始行为事件在前端内存中按场景聚合后再批量上报，服务端始终无法还原用户的具体操作序列；③ **原文不落库**——短文本情感分析的正文仅在单次请求的内存生命周期内存在，不写入任何数据表、不写入运行日志；④ **默认关闭（opt-in）**——系统出厂状态为关闭，须用户阅读采集清单后主动授权方可启用，并可分行为、分文本细粒度关闭；⑤ **严格的一人一份访问控制**——行为特征与推测候选表的 userId 一律取自 JWT 令牌，系统不接受任何来自前端的用户标识入参，**即使是管理员角色也无权查询他人的行为元数据**，其对用户行为数据的保护强度高于系统的普通内容数据；⑥ **全程可撤回**——支持一键关闭、一键删除与数据 CSV 导出（数据可携带权），所有开关变更写入隐私审计日志，行为数据默认保留 180 天后由定时任务物理清除。上述机制使系统在具备情绪感知能力的同时，满足《个人信息保护法》中关于最小必要、知情同意、目的限定与可撤回性的合规要求。

### 7.3 创新点三：人机协同的"推测—确认—纠偏"闭环

> 为避免"系统替用户做决定"这一常见伦理争议，本文在系统推测与正式数据之间设置了不可跳过的确认环节：推测结果**永不直接入库**，而是以待确认候选的形式呈现给用户，由用户选择采用、修改后采用或忽略。用户最终的真实选择被回写为 `confirm_emotion` 字段，与系统推测值形成对照，从而在系统运行过程中自然积累带标注的评价样本。基于该闭环，本文设计了采纳率与精确命中率两项在线评价指标，使推测算法的有效性可以在真实使用数据上被持续度量，而非依赖离线数据集的人为评测。这一"推测在前、人做终判、反馈纠偏"的机制，既保证了正式情绪数据的真实性与可信度，也使系统的智能化程度可被实证检验。

### 7.4 论文实验章节可写的内容

| 指标 | 定义 | 数据来源 |
|---|---|---|

## 8. 答辩隐私风险问答（老师大概率会追问）

**Q1：你这个"无感记录"是不是在监控用户？**
> 不是。系统只采集四类聚合数值（停留时长、点击次数、进入次数、时段掩码），全部由一个位图整数和几个计数器表达。它回答不了"用户今天点了什么、写了什么、听了什么"。用户随笔的分析是用户主动点按钮触发的，正文不落库，请求结束即销毁。

**Q2：为什么这些行为数据连管理员都不能看？**
> 因为行为元数据比内容更容易被忽视，也更敏感——它能反映用户的生活作息、情绪低谷时段。所以我对它施加了比普通内容更严格的访问控制：`userId` 只从 JWT 取，接口不接受任何用户标识入参，管理员角色同样不可查询。这在权限矩阵里是明写的一条。

**Q3：系统猜错了会不会误导用户？**
> 有三道防线。第一，低于 0.45 置信度不输出推荐，宁可不猜；第二，推测只是"待确认候选"，不入正式库，用户必须手动点采用或改写后才入库；第三，入库的数据永久带 `source=2` 标记，所有统计图表里与手动记录分色渲染，用户随时知道哪条是自己写的、哪条是系统猜的。

**Q4：符合《个人信息保护法》吗？**
> 设计上对齐了四条：最小必要（只采聚合值）、知情同意（默认关闭 + 授权弹窗列明采集清单）、目的限定（数据只用于本人情绪推测，不用于推荐、不共享给第三方）、可撤回可删除可导出（一键关闭、一键清空、CSV 导出 + 保留期到期物理清除）。并且每一步操作都有审计日志。

**Q5：这些数据会不会被用来二次训练？**
> 有一个刻意的设计：行为 KNN 的历史样本**只取 `source=1` 的手动记录**，排除掉所有系统推测出来的数据。这是为了防止"用推测数据训练推测模型"导致的自我强化偏差，也从工程上切断了数据污染链。
