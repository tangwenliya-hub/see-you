## 一、性能优化：统计接口从内存聚合到 SQL 聚合（实测对比）

### 背景（问题描述）

初版统计接口把整张 `psy_diary` 表用 `list()` 拉进 Java 内存，再 for 循环计数/求平均：
- 单次请求传输全部日记正文与图片地址（大文本白查）；
- 耗时随数据量线性增长（O(n)）；
- 全站统计接口游客可访问，等于把最慢的接口开放，构成 DoS 放大面。

### 方案

1. 聚合下推 MySQL：`GROUP BY` / `COUNT` / `AVG(CASE emotion WHEN 1 THEN 100 ...)`（见 `StatisticsMapper`）；
2. A 类全站接口加 30 秒内存缓存（ConcurrentHashMap + TTL）；
3. 个人趋势/热力图只取「日期 + 情绪」两列，并用 `MAX(diary_id)` 子查询做"每天只取最后一条"的去重；
4. 新增联合索引 `(user_id, diary_date)`。

### 实测数据（同一台机器、同一 jar 内新旧两版对照，15 轮取平均）

| 接口 | 改造前 | 改造后 | 提升倍数 |
|---|---|---|---|
| 全站情绪分布 | 722 ms | 2.4 ms（首次 24 ms） | ~300× |
| 月度情绪趋势 | 733 ms | 2.0 ms（首次 27 ms） | ~360× |
| 活跃用户 Top5 | 652 ms | 3.4 ms（首次 20 ms） | ~190× |
| 我的概览 | 657 ms | 124 ms | ~5× |
| 我的热力图 | 585 ms | 25 ms | ~23× |

> 压测环境：灌入 2 万条日记（真实数据 830 条）；"首次"为缓存未命中的首次请求。
> 改造前后返回 JSON 逐字段比对一致，前端零改动。

### 论文写法建议
可作为"数据库设计与查询优化"一章：问题（内存聚合 O(n)）→ 方案（索引 + 聚合下推 + 缓存 + 列裁剪）→ 实验（上表）→ 结论（响应时间与数据量解耦）。

## 二、安全设计：从 13 类越权到纵深防御

### 发现并修复的漏洞类型（答辩可讲"我们做了什么"）

| 漏洞 | 危害 | 修复方案 |
|---|---|---|
| 验证码下发（devCode） | 仅凭账号名即可重置任意账号密码 | 仅开发开关开启且未配 SMTP 时回显；生产不下发 |
| WebSocket 握手无鉴权 | 伪造 `role=admin` 接收全站反馈 | 握手强制校验 JWT + 会话表 |
| IDOR（越权访问）×9 | 任意读/删他人日记摘要、测评记录、播放历史、点赞收藏、反馈 | `userId` 一律从 token 取；资源归属校验；管理员显式代查 |
| 冒名写操作 | 伪造 userId 发评论/写记录 | 服务端强制 `setUserId(token.uid)` |
| 禁用账号可登录 | 封禁形同虚设 | 登录校验 `status=1` |
| 弱随机重置码 | 6 位码可被预测遍历 | `Math.random()` → `SecureRandom` |
| JWT 密钥硬编码 | 泄漏即可伪造任意身份 | 密钥外置为 `jwt.secret` 配置（环境变量优先） |
| 前端角色伪造 | 改 localStorage 可见后台页面结构 | 路由守卫改为调 `/user/info` 以服务端 role 为准（30s 缓存） |

### 纵深防御层次（可画成架构图）

1. **入口层**：JWT 拦截器统一鉴权 + 白名单最小化 + 管理员路径规则；
2. **会话层**：`sys_user_session` 服务端会话表（踢下线立即失效）+ 登录失败锁定 + 图形验证码；
3. **业务层**：资源归属校验（本人或管理员）+ 归属字段服务端强制写入；
4. **数据层**：BCrypt 密码哈希、上传文件类型白名单 + 路径穿越防护、分页上限（`PageLimit` 截到 100）。

## 三、可视化设计：9 类图表与「情绪指数」模型

### 情绪指数量化

9 种情绪映射到 0~100 指数（1 开心→100、7 兴奋→90、8 满足→85、2 平静→70、3 疲惫→50、9 其他→55、6 焦虑→40、5 生气→25、4 难过→20），使离散情绪标签可参与平均、趋势与回归计算。前端 `utils/constants.js` 与后端 `StatisticsController.EMOTION_INDEX` 双端一致。

### 图表清单（数据看板）

| 图表 | 类型 | 数据来源 | 技术点 |
|---|---|---|---|
| 打卡热力图 | ECharts calendar heatmap | `my/heatmap`（按天去重） | 365 天日历坐标 |
| 情绪指数趋势 | line + area 渐变 | `my/trend` | rAF 合并 resize、`notMerge` 防残留 |
| 情绪分布 | 环形饼图 | `my/emotion`（GROUP BY） | 按情绪配色 |
| 月度走势 | 柱线混合双 y 轴 | `my/monthly` | 天数 + 平均指数 |
| 测评分数变化 | 多系列折线 | `my/testTrend` | 动态图例、按量表分组 |
| **睡眠×情绪散点 + 回归线** | scatter + 最小二乘 line | `my/scatter`（近 90 天样本） | 前端计算回归系数与相关系数 r |
| **未来 7 天预测带** | line + 置信区间带 | `my/trend` 外推 | 80% 置信区间（±1.28σ） |
| **一周情绪流向** | sankey 桑基图 | `my/sankey`（星期×情绪矩阵） | gradient 流线、邻接高亮 |
| **心情关键词** | wordCloud 词云 | `my/keywords` | 后端中文二元分词 + 停用字过滤 |

### 工程细节（可写"前端工程化"小节）

- **useChart 组合式函数**：15+ 个 ECharts 实例统一 init/resize/dispose；`prune()` 回收被 `v-if` 移除的僵尸实例；全局单例 resize 监听（rAF 合并），卸载自动解绑，杜绝内存泄漏；
- **`notMerge: true`**：切换时间范围时丢弃旧 series，修复"30 天切 7 天残留旧类目"的 bug；
- **主题跟随**：图表颜色全部从 CSS 变量（`--c-hex` 等）运行时读取，切主题/深色模式自动重绘。

## 四、中文关键词提取（无词典轻量方案）

词云没有引入分词库（jieba 等会显著增大依赖），而是在后端实现约 30 行的**二元组统计**：
1. 取用户近 180 天日记正文（最多 300 条）；
2. 相邻两个汉字组成词（二元 bigram），跳过含停用字的组合（"的了是在我…"约 60 字）；
3. 频次 ≥5 的词按频率排序取前 40 返回。

实测对「今天/心情/工作/压力/考试」这类高频词提取效果良好；优点是零依赖、O(n) 单次扫描；局限是无法切分三字以上专有名词。这是"工程权衡"的好例子，答辩被问到分词时可以主动讲。

## 五、账号安全体系（可独立成"系统安全设计"一节）

- 服务端图形验证码（登录必填，一次性消费，5 分钟过期）
- 登录失败 5 次锁定 10 分钟（`sys_login_attempt`）
- 邮箱找回密码（SecureRandom 6 位码，10 分钟有效，一次性使用）
- 多设备会话管理（设备列表 / 踢出指定设备 / 一键踢出其他设备；"在线"= 30 分钟内有心跳，心跳按 60 秒节流写库）
- 生产环境静音 console.log、异常信息脱敏（GlobalExceptionHandler 仅业务异常回传 message，兜底统一"服务器内部错误"）

## 七、断记提醒（用户留存设计的轻量实现）

主页顶部在「连续记录中断 ≥2 天」时显示提醒条：「🌱 你已经 N 天没写日记啦，今天也来记录一下吧」，带「去记录」直达写日记页；关闭后当天不再出现（localStorage 记录关闭日期，次日自动恢复）。设计取舍：
- **不打扰新用户**：从未写过日记不提醒（避免注册即劝退）；
- **零后端成本**：完全复用主页已加载的日记列表在前端计算，不增加任何请求；
- 答辩可讲：这是"轻量 nudge（助推）"设计——在恰当的时机用最低的成本唤回用户。
