# 绪见 · 安全与性能清单

> 面试高频追问点：「你怎么保证安全」「数据量上来之后怎么办」。本文是可直接讲述的清单。

---

## 一、账号与认证安全

| 措施 | 实现 | 说明 |
|---|---|---|
| 密码哈希 | BCrypt | 不明文存储，不自己造轮子 |
| 令牌 | JWT，密钥**外部注入** | 无内置默认密钥，避免任何人自签 token |
| 图形验证码 | 服务端生成 + 校验 | 防暴力撞库 |
| 登录失败锁定 | 连续 5 次锁 10 分钟 | `sys_login_attempt` 计数 + `lock_until` |
| 会话管理 | `sys_user_session` | 可查看在线设备、踢出指定会话、下线其他设备 |
| 找回密码 | 6 位 SecureRandom + 10 分钟过期 + 一次性 | 凭证用后即废 |

## 二、越权防护（水平/垂直）

**统一约定：个人数据的归属一律以 token 为准，不信前端传参。**

- 普通用户传他人 `userId` 时，Controller **强制覆盖为本人的 id**（`if (!isAdmin()) userId = viewerId();`）
- 写操作（点赞/收藏/评论/日记）的 `user_id` 由服务端从 token 写入，**不接收前端字段**
- 后台路由调用服务端接口按返回角色校验，改本地 localStorage 无法绕过
- 无感记录与预警模块的 Mapper SQL **一律带 `user_id`**，Controller 不接 userId 入参——**管理员也查不到他人行为数据**
- 行为特征表只有整数与枚举列：不含 URL、不含点击目标 DOM、不含任何用户输入文本

> 已用脚本对 25 个 Controller 做过入参审计：存在的 `userId` 参数均属"管理员可代查"场景，且都有角色判断兜底。

## 三、上传安全

`UploadController` 的四道防线：

1. **目录白名单**：`dir` 只能取 `banner/cover/avatar/bg/img/diary/user/video/audio`，杜绝 `../../` 路径穿越
2. **扩展名白名单**：按目录类型限定，禁止 `.jsp/.exe/.html` 等可执行内容
3. **大小限制**：图片 5MB、音频 50MB、视频 200MB
4. **落盘前复核**：用 `getCanonicalPath` 确认最终路径仍在根目录内

## 四、配置与密钥安全（2026-10-28 整改）

整改前 `application.yml` 里明文放着数据库密码与 AI Key，这是**推公开仓库就会泄露**的级别。现在：

- `application.yml` **只保留占位符**（`__SET_JWT_SECRET__` 一类），不再有任何真实凭据
- 真实值放在 `.gitignore` 忽略的 `application-local.yml`，或由环境变量注入
- 新增 `application-prod.yml`：关闭 SQL 日志、关闭 dev-captcha-log、路径走容器绝对路径
- 提供 `.env.example`、`application-local.yml.example` 两个模板（模板本身入库，真值不入库）

> ⚠️ **已发生的泄露**：仓库历史提交中曾有明文密钥，且已推送到 Gitee。
> 清理工作树不会清除 Git 历史，**必须先轮换密钥**（重生成 AI Key、改数据库密码、换 JWT 密钥）。
> 详见 `docs/部署说明.md` 第 5.4 节。

## 五、索引与查询性能

**核心思路：聚合下推 MySQL，不把明细拉回内存算。**

| 表 | 索引 | 作用 |
|---|---|---|
| `psy_diary` | `idx_uid_date (user_id, diary_date)` | 个人统计（趋势/热力图/散点）全部靠它，实测 2 万条日记下统计接口从 ~700ms 降到 2~25ms |
| `psy_diary` | `idx_source` | 无感记录只取 `source=1` 的手动日记做训练样本 |
| `psy_like` / `psy_collect` | `uk_user_resource` | 防并发重复点赞，同时加速状态查询 |
| `psy_comment` | `idx_resource_status` | 资源详情页按资源查已审核评论 |
| `psy_history` | `uk_user_resource` | 播放历史 upsert 去重 |
| `psy_test_record` | `idx_user_time` | 个人中心按时间倒序列测评 |
| `psy_feedback` | `idx_user_deleted` | 列表查询恒带 `deleted` 过滤 |
| `psy_ai_chat` | `idx_ai_user_session` | 按会话重建上下文（最近 10 轮） |
| `sys_user_session` | `idx_token` | 每次请求都要按 token 查会话 |

**2026-10-29 补充**：`psy_diary` 增加覆盖索引 `idx_uid_source_date_id (user_id, source, diary_date, diary_id)`，
「按天取最后一篇」的 4 条统计 SQL 因此可以走 index-only scan；同时删掉单列 `idx_source`
（基数只有 1/2，优化器基本不用，只是给写日记增加一次索引维护）。脚本：`sql/migration/20261029_diary_day_rule.sql`。

**2026-10-29 补充（前端首屏）**：数据看板 16 个 ECharts 实例改为**进入视口才 init**（`useChart(el, name, { lazy: true })`，
IntersectionObserver + 240px 预取），首屏请求由「一次 9 并发 + 3 并发」改为**每批限 3 个的受控并发**。
改造前首屏要同时 init 16 个画布并打 20+ 请求，低配机器上会有 3~5 秒白屏；改造后进入视口即渲染，滚动到底部才付剩余成本。

**2026-10-28 补充**：新增 5 个索引，并删除 `psy_diary` 上一条**完全重复的冗余索引**（`idx_user_date` 与 `idx_uid_date` 列相同，白占写入开销）。脚本见 `sql/migration/20261028_performance_indexes.sql`，幂等可重复执行。

## 六、其他性能实践

- **按天取数的去重策略**：趋势/热力图用 `MAX(diary_id)` 子查询取"每天最后一条"，避免同一天多篇日记把明细全拉回内存
- **AI 对话超时控制**：连接 5s / 读取 30s，超时给友好提示而不是挂死；失败降级到本地关键词库
- **图表实例托管**：`useChart` 统一处理 ECharts 实例的注册、resize、卸载销毁，避免内存泄漏
- **前端路由懒加载**：所有页面 `() => import(...)`，首屏只加载落地页

## 七、2026-10-28 第三轮：可演示性与部署可用性

| 项 | 问题 | 处理 |
|---|---|---|
| **可执行 jar 缺失 repackage** | `mvn package` 产出的是 418KB 普通 jar（无 `Main-Class`），`java -jar` 报"没有主清单属性" → `deploy/Dockerfile.backend` 与一键部署脚本**都会启动失败** | `pom.xml` 的 `spring-boot-maven-plugin` 显式声明 `repackage` execution；重新打包产出 **63MB fat jar**，`java -jar` 实测可启动 |
| 限流无法关闭 | 阈值硬编码在拦截器里，答辩现场反复登录/连发 AI 可能被 429 挡住 | 改为 `app.rate-limit.enabled`（总开关）+ `app.rate-limit.rules`（逐条覆盖阈值），演示时 `--app.rate-limit.enabled=false` 一键关闭 |
| 无感模块无数据可演示 | `psy_behavior_feature` 为 0 条，模块打开是空的，创新点讲不出来 | 新增 `sql/migration/20261028_seed_sense_demo.sql`（60 天 × 8 场景 = 480 条，幂等），配套 `docs/无感记录演示指南.md` |
| 改动未经真实例验证 | 前两轮改动只过了编译与单测，运行中的实例是旧代码 | 新起实例实测：限流生效（第 21 次 429）、登录/鉴权/游客放行/无感推测/预警全部 200 |
